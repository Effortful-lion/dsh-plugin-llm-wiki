配套 [PRD.md](./PRD.md) ｜ 版本 v0.3.0 ｜ 2026-11

## 一、分两层看这份文档

| 层 | 含义 | 承诺强度 |
|---|---|---|
| **交付期 M0–M5** | 本期 PRD 写清楚、要验收的部分 | 有验收标准，做不完不算交付 |
| **规划期 P1–P5** | 想到了、值得做、但现在不做 | 只有目标与进入判据，**不承诺时间** |

判断一条需求属于哪一层，只看一个问题：**它有没有前置依赖还没验证？** 有 → 规划；没有 → 交付。

RAG 和知识空间都属于"有前置依赖"：RAG 要先有稳定页结构和检索基线才能测出增益；多库要先证明单库在 800 页内不够用。所以进规划，不进 PRD 正文。

## 三、规划期

### P1 检索增强（RAG）｜可选模块，默认关闭

**定位不变**：只做入口定位，不做上下文扩充。用户说一句话 → 解出相关页的引用与 id → 拿着 id 在 wiki 里推理。

**先做零成本的替代（v1 内已写入 PRD §4.6）**

| 手段 | 做法 | 成本 |
|---|---|---|
| bigram 切分 | 「胰岛素抵抗」→ 胰岛/岛素/素抵/抵抗，不依赖词表 | 0 token，纯代码 |
| 别名索引 | 每页维护 2–5 个别名，写进 frontmatter | 0 token + 少量人工 |
| 同义词表 | `.wiki/synonyms.yml`，可开可关 | 0 token |

经验判断：这三条能吃掉大部分「搜不到」。RAG 是最后一档，不是第一档。

**RAG 真正要花什么（这是决定做不做的关键）**

| 成本项 | 量级 | 说明 |
|---|---|---|
| 建库嵌入 | 页数 × ~400 token | 1000 页 ≈ 40 万 token，等于一次性「读 100 页」 |
| 增量重嵌 | 改动页 × 400 token | 合并一个提案约 1–3 页 |
| 查询嵌入 | 每次 ~20–30 token | query 很短，可忽略 |
| 存储 | 每页 1–2KB | 1000 页 ≈ 1.5MB，可忽略 |
| **调参成本** | **数天** | 排序权重、RRF 融合参数、相似阈值——这才是真正的成本 |

结论：**token 不贵，贵在调参和维护两套检索的排序。** 所以做成开关（面板设置里一个 toggle，默认关），而不是默认开启的半残状态——「开着但从不调参」比不做更糟，因为它会让检索结果时好时坏，你又不知道是哪一路在起作用。

**进入判据**（三条同时满足才启动）：

1. 页数 ≥ 300；
2. bigram + 别名 + 同义词已上线并稳定 ≥ 1 个月；
3. 仍有每周 ≥ 3 次「搜不到」的实例记录（由 J09 缺口补页的日志自动统计，不靠回忆）。

**必须先定**：embedding 提供方（本地 Ollama / 云端）、向量存放位置。建议**库外可重建缓存**——放库内会进 git 变成二进制噪音，放库外丢同步则一键重建即可。

**明确不做**：raw chunk 向量化；检索结果直接喂模型总结。这两条会导致上下文双份消耗。

### P2 知识空间（多库）｜**当前不启动**

> 用户已选择「一个超级大脑装所有领域」。本节保留为**逃生路径**：只有在单库超过 800 页、或需要独立采集/共享/同步时才启用。

**空间 vs 库的分工**（这条已定，写死在文档里，避免以后反复讨论）：

| 层 | 是什么 | 负责什么 |
|---|---|---|
| 空间 | 一个 Obsidian vault / 一个 git 仓库 / 一个同步单元 | 库注册表、跨库汇总（只出数字）、库级操作（git、备份、迁移） |
| 库 | 一套 `0-inbox 1-raw 2-wiki 3-review` + 自己的 index/log/采集任务 | 知识本身、检索、提案、领域过滤 |

**三条硬规则**：

1. **每个 brain 必须是独立 vault**，不能是同一 vault 下的子目录。Obsidian 一次只能开一个 vault，子目录会让全局搜索与反链跨库混在一起，"隔离"是假的。
2. **跨库只用引用，不嵌入**：写 `see: <库名>/<页 id>` 作为纯文本外链，**不解析、不入链接图、不参与检索**。跨库一旦进索引，检索就要并集，等于又变回单库。
3. **拆库判据**：需要「独立采集任务 / 独立人格与 preset / 独立共享与权限」才拆；只是"话题不同"用 `domain` 字段。

**进入判据**：任一成立即启动——单库 > 800 页且检索变慢；需要给他人只读访问；两个领域需要完全不同的同步与备份策略。

**成本**：库里空的时候拆库几乎零成本；库有内容之后拆库要做链接重写 + 索引重建 + 采集任务迁移，按每个库半天估算。

**先不做的事**：库切换器 UI、跨库检索、库间迁移工具。单库没跑够 3 个月不做这三样。

### P3 摄取扩展

| 项 | 目标 | 前置 |
|---|---|---|
| 浏览器剪藏 | 网页正文 + 元信息一键入 inbox | 无 |
| 邮件归档 | 指定发件人 → inbox | 无 |
| 目录监听 | 指定文件夹新文件自动入 inbox | 无 |

音频转写已从本项**提前到 v1**（PRD §6.1），因为它复用的是宿主现成能力，没有前置依赖。代价是转写误差会直接进入素材层，所以转写页标 `confidence: low`，编译时强制人工确认要点。

---

### P4 协作与发布

- **只读发布**：把 `2-wiki` 渲染成静态站点（给人看，不给人改）。
- **团队共享**：多人各自写提案，统一合并；需要提案加"作者"字段与合并冲突处理。
- **权限**：按库/按目录的读权限。这条会推翻当前"单写者锁"的假设，需要重新设计。

**进入判据**：出现第二个真实使用者，或者需要对外交付知识时。

---

### P5 可视化

- 图谱视图（页与链接的力导向图）——注意：图的收益是"发现孤岛"，而孤岛已经由 lint 在文本层报出来了，所以优先级低。
- 健康趋势（页数/提案/过期数的时间序列）。
- 时间线（按 `updated` 排的知识演进）。

**进入判据**：面板 v1 用满 1 个月，仍然觉得"光看数字不够"。

## 四、进入判据汇总（什么时候允许把规划提前）

| 规划项 | 允许提前的条件 |
|---|---|
| RAG | 页数 ≥300 且每周 ≥3 次"搜不到" |
| 多库 | 单库 >800 页，或需要独立采集/共享/同步 |
| 音频 | PDF/图片预处理稳定运行 ≥1 个月 |
| 团队 | 出现第二个真实使用者 |
| 图谱 | 面板用满 1 个月仍有信息缺口 |

判据的作用不是限制你，而是**防止在验证不足的时候花时间做没有收益的事**——这套设计最容易的失败方式不是做错，是在库还空着的时候把架构做得太大。

## 五、永久非目标

以下不是"以后做"，是**确定不做**：

- agent 自动写正文并直接生效（自动化只覆盖机械动作）；
- 把 raw 原文 chunk 塞进上下文交给模型总结；
- 引入数据库或私有格式（库必须是纯 Markdown，拔掉插件也能用）；
- 自动裁决矛盾（可以自动检测、自动出提案，但不能自动决定哪个版本对）；
- 跨库链接图（会让检索退化成并集）。
